# 公众号长文写作

这份 skill 记录的是一位作者的写作习惯和改稿标准。它来自作者几篇长文从选题到定稿的完整过程，作者在改稿中提出的每条意见都写进了下面的规则。

写作时如果环境里装了 human-writing（活人感写作，https://github.com/KKKKhazix/human-writing ），先按它的材料检查和禁用项走，再按本文件的作者偏好调整。两者冲突时，以本文件为准。

## 一、这位作者是谁，文章写给谁

- 作者是一个关心行业、也懂一点技术和商业的普通人，用第一人称"我"说话。文章同时是公开发表的公众号长文和求职作品集，所以要兼顾传播和专业度。
- 读者是对 AI 感兴趣、但不了解背景的普通人。面试官也会读，所以要让人看出作者能从普通人的体感，一路讲到技术原因和行业账本。
- 语气平视、口语、偶尔自嘲。拒绝布道腔、分析师腔、论文腔和公关软文腔。
- 不神化任何一家厂商，也不死磕单个模型，盯的是底层技术和产品机制怎么演进。

## 二、动笔前

### 流程固定，一步一停

先确认选题和主旨，再确立大纲，作者确认以后才写正文。每一步都等作者点头。作者说"先改大纲"时，正文立刻停下。

### 选题要有自己的角度

- 作者最在意的是**不同质化**。读者读完要能多一个看问题的角度，风格可以轻松好读，但内容不能浮于表面。
- 大纲交出去以前先自查，每一章是不是只在罗列现象和数据。如果是，就往下挖一层机制。
- 章节标题和章节内容必须对得上。标题写的问题，正文要真的回答。
- 一个选题里出现了视角完全不同的分支，就建议拆成单独一篇，不要硬塞进来压扁它。
- 没有定论的大问题，放在结尾当作一个留给读者的思考点，不下结论。

### 定大纲前先查有没有人写过

- 大纲里的主要观点，先搜一遍中英文资料，看有没有人已经写过。已经被写过的观点，压缩成一章背景交代，不当主论点。
- 主线换成别人还没怎么讲过的角度，并说明这个角度和已有观点的差别。
- 作者的几篇文章之间如果能形成一条可以辨认的思考线，就在文中点一句，把前后几篇接起来。

### 案例只用真实的

- **绝不虚构故事**，不编"我表姐""我室友"这类人物，也不替作者编亲身经历和当时的反应。
- 作者给出的个人经历，只能按作者说的写，不能扩写成别的经历。作者说"没有深度体验过"，正文里就不能写成深度用户。
- 每个案例都要能查到公开报道，写进正文前核对时间、数字和出处。**文章里不放参考资料**，出处在对话里交给作者，方便核对。
- 需要作者本人经历的地方，一次最多问三个问题。作者给了链接，自己去看，能截图就截一张。
- 案例要贴近国内一线的真实体感，比如朋友圈写真、下沉市场付费、短视频平台上刷到的爆款。
- 作者记得、但查不到原文的引语，用"我记得在……里看到过这样一句话，大意是……"来写，保留余地。
- 介绍一个产品时，它的核心功能要逐条核实，每条配一个查得到的案例。查不到依据的功能一律不写。写错一个功能，内行人一眼就看穿，整篇文章就站不住了。
- 作者对技术、产品之间关系的说法，也要核实。说法不对，直接告诉作者哪里不对、真实关系是什么，再决定写不写。
- 不给作者编动作和心理，比如"我盯着它的介绍看了很久""后来我去翻了它的文档"。作者没说过的，就不写成作者做过的。
- 作者说是在书里读到的例子，不能写成作者自己想出来的。查不到出处时，写"我在一本书里读到过"，不写"书名忘了"，后者显得不专业。

### 演进类题材可以用因果链

写技术、产品演进这类题材时，每一章可以按下面的顺序推进；其他题材不强求，按观点本身的推进来组织。不管用哪种结构，每章的进入方式都要换，有的从一段视频开始，有的从一笔生意开始，有的从一个骗局开始，避免像机器打拍子。

1. 生活里的体感，普通人在手机里看到了什么、哪里露了馅
2. 当时卡在哪，背后的真实瓶颈
3. 什么技术或机制把它解开了
4. 市场随之发生了什么，引出下一章

开头不预告全文结构，结尾不把全文再总结一遍。引子埋下的问题或伏笔，结尾要扣回来。

## 三、写的时候

### 标题

- 作者的标题习惯是，有"我"或者一个具体的位置，直接说清楚这篇聊什么，口语，不卖关子。比如《被奶龙缠上以后，我把 AI 视频这几年翻了一遍》《从一个单身狗的视角看情感陪伴》。
- 不用科技媒体式的噱头标题，比如《当 AI 有了自己的手机号》，这种标题看不出是谁在说、聊的是什么。
- 给两三个候选，句式参照作者已有的标题，说明推荐哪个、为什么。

### 引子

- 开头直接从现象或热度切进去，再落到最打动作者的那一个具体对象上，紧接着把这个对象的核心特点讲清楚。
- 不交代作者从哪里看到的信息，比如"我是在一篇文章里读到它的"，这种交代显得作者不关注行业。
- 讲一个趋势时，把大厂、头部公司跟进的具体产品和时间列出来，用事实说明这个趋势有多重要。
- 书、理论、框架不要在引子里突然冒出来。放到真正用它分析问题的那一章开头，并写清楚眼前这件事为什么让作者想起它。

### 引用和理论

- 引用一句名言或书里的话，只取要用的那部分，不在正文里展开出处考证。出处在对话里交给作者，不写进文章。
- 介绍一本书或一套理论，先把核心概念和核心结论讲清楚，再拿它对照眼前的案例。衔接处要写出两者为什么能对上。

### 概念分层

- 作者给出了分层框架，就照作者的框架写，每一层写明它的核心特征。
- 划分标准要准确，用的是各层之间真正的区别。似是而非的标准会被内行一眼看出来，写之前先核实。

### 不写读者都知道的话

- 读者一看就懂、不说也不影响理解的交代，一律删掉。比如"我用这个工具干什么，交代一句，它会自己干什么"。
- 解释一个商业现象，先写最直接的原因，比如竞争和利益，再写更深一层的原因。

### 口吻

- 引子是全文口吻的样板，参考 `references/voice-sample.md`。
- 允许作者式的玩笑和自嘲，比如"我是真没招了""我活到头了""也有可能我原本就这么帅"，但要从眼前的事情里自然长出来，不硬塞。
- 用外号或调侃称呼人物时直接用，不用"因为""也就是"解释来历，让笑点从后面的事里长出来。读者熟悉的人物，直接用大家熟悉的叫法。
- 人物介绍不写简历，只留和眼前这件事有关的一句。头衔、任职年份、作品清单这类背景，正文用不上就不写。
- 不要把作者写成"我们这种刷手机的人"，这样显得不专业。写"对于刷手机的人"，或者"普通观众"。

### 用词

- 用行业里的说法。反复生成挑结果叫**抽卡**，不说"一遍遍刷"。
- 技术解释用日常比喻，而且比喻要准。比如扩散模型的生成过程，像美术生画素描，先起稿，再铺大关系，最后深入刻画。
- 解释要说人话。"质感在海量图片里规律很稳"这种抽象说法要改成"这些东西在各种图片里的样子都差不多，AI 看得多了，很快就学会了"。
- 引子和叙事部分的数字可以模糊，比如"播放量涨到了百万"；行业数据部分保留精确数字和出处。
- 数字的含义要准确。播放量是次数，不能写成"骗了两亿人"。
- 不写"今年""去年"，写具体年份，文章会被人隔很久再翻出来读。
- 同一个东西全文用同一个说法，比如"推荐栏"和"推荐页"不能混用。

### 衔接，这是作者最在意的

作者改稿时最常指出的问题是"衔接生硬"和"像被鬼上身了"。写完每段都要检查下面几条。

- **不写突然冒出来的旁白句。** 比如"故事的后半段，对做产品的人更有用""哑巴的事放到下一章说"，这种跳出来对读者说话的句子一律删掉，直接讲事。
- **语义转折要有转折词。** 前后意思相反时，用"但是""可""不过"连起来。比如"画面已经像实拍了，但是拍什么、怎么拍，还由不得人"。
- **因果词要成立。** "所以"前面必须真的有原因，推不出来就换成"回头看"之类的说法。
- **不留孤零零的短句段落。** 接不住上一段的单句段，就并进上一段，或者补上承接。
- **前后两段之间要有桥。** 两件事之间缺一步推理时，补一句把它们连起来。
- **问句要完整。** 写"三秒钟已经能让人掉眼泪了，那三十秒呢？"，不写"三十秒呢？"。
- **呼应和笑点要接对对象。** 结尾的玩笑紧挨着哪句话，读者就会把它和哪句话连起来读。笑点接的不是它真正呼应的那件事时，补一句桥，或者调整前一句的顺序。
- **首尾呼应换个措辞。** 引子和结尾用同一个开头词，比如两处都是"两三年前"，读起来像写重复了。
- **悬念不要被打断。** 前面抛出的问题，中间不要插一整节无关内容，再隔很远才回答。

### 禁用项

- 不用冒号做提示，不用破折号。
- 不用"不是……而是……"这类翻案句，判断直接从正面说。
- 不用"说白了""说到底""值得注意的是"这类路标，不用"赋能""底层逻辑""降本增效"这类黑话。
- 不用"没有凭空消失"这类总结腔收尾。

## 四、排版

- 每章加 3 到 4 个小标题，让小标题本身能当目录读。
- 每章的核心观点和核心论据都要加粗标出来，可以是一句话，也可以是几个关键词。作者很在意这一点，宁可每章标四到六处，也不能漏掉核心，但不要整段加粗。
- 写 Markdown 加粗时，句末标点放在加粗符号外面，写成 `**这是重点**。`，不写成 `**这是重点。**后面的字`。后一种写法在很多编辑器里识别不了，星号会直接露在正文里。交稿前逐个检查全文的加粗。
- 手机上看是一大块的段落，从意思转折的地方拆成两段。一段里讲了两件不同的事，也要拆开。
- 全文正文用中文标点，引号统一用中文引号 “”。转述一句具体的指令或提示词时，给它加上引号。

## 五、配图

### 数量和取舍

- 正文配图控制在 **5 张以内**。图文结合是为了让读者读完，不是为了把文字再画一遍。
- **不要把正文内容用图再展示一遍。** 文字已经讲清楚的流程、数字、对比，不配图。只有非常抽象、文字很难想象的机制，才考虑配示意图。
- 配图以生成的封面插画和机制图为主，真实截图只留 1 到 2 张。截图用在正文写不出来的现场和证据上，比如爆款视频、AI 露馅的画面、前后对比。生成的图也不要多，放在文字最难想象的地方。
- **风格不能割裂。** 一组真实截图里只夹一张自己做的示意图，会显得突兀，这张示意图通常应该删掉。要用示意图，就成组使用，风格统一。

### 尺寸和格式

- 全部用横版，宽度统一为 1280。能裁成 16:9 的都裁成 16:9；宽幅图保持同一种比例。
- 竖向拼接的对比图，改成左右并排的横版。作者自己标的文字和圈注要保留。
- 每张图下面加一行图注，格式是"▲ 说明，图源：来源"。
- 公众号封面比例是 2.35:1，主体偏一侧，另一侧留白放标题。

### 找不到的图

- 先降低要求。局部放大、画圈、拼图这些加工都由 Claude 来做，作者只需要找到原图或者截一帧。
- 给出具体的搜索关键词和来源，比如事实核查文章、新闻报道配图。
- 实在找不到，就删掉这处配图，确保正文不依赖它也能读通。
- 图片内容要和正文对得上。截图里的数字和正文写的不一致时，以截图为准改正文，并提醒作者核对。

### 生图模型

- **绝不用生图模型伪造看起来真实的截图**，比如聊天记录、社交媒体帖子、新闻页面。需要这类图，只能由作者去截真实的。
- 生图只用来做两类图。一类是封面插画，一类是机制图。
- 每篇文章的配图都用同一套形式，一张封面插画（写一套完整提示词），作者自己截的真实截图，加上套用下面模板的机制图。正文定稿后，把封面和机制图的提示词一起交给作者。
- 作者的机制图模板如下，每张图把对应章节的机制写进摘要里，写清节点、箭头方向和标注，标注要短。

```
你现在是一名经验丰富的科研绘图设计师。请根据以下文本内容，生成符合学术发表标准的科研机制图。请结合我发给你的文本摘要/研究内容生成BioRender扁平化风格、柔和的科学配色、纯白色背景、可用于科研发表的机制图。请使用标准的科学符号、箭头表示因果关系，关键分子/元素用规范名称标注。图中文字默认使用中文。保持从左到右或从上到下的逻辑流程，层次清晰，留白适当
摘要内容：{
（这张图的节点、箭头、标注和数据来源）
}
```

- 封面插画写一套完整提示词，写清人物、场景、配色、比例，并注明画面中不要出现文字。
- 交提示词时提醒作者，生图模型常把中文画成乱码，生成后要逐字检查。

### 标记格式

交付的 Markdown 需要配图的地方用单独一行标记，标明谁来做。

```
【封面 · 插画】画面主体和场景的一句话描述
【配图01 · 需你截】要截的页面或画面，以及截哪一部分
【配图02 · 机制图】这张图要讲清楚的机制
【配图03 · 已做好 · 03_文件名.jpg】这张图展示的内容
```

## 六、交付和改稿

- 交付格式默认是 Markdown。作者要带图的版本时，用相对路径引用 images 文件夹，打包成 zip 发给作者，并提醒他，粘到 mdnice 这类公众号排版工具时图片要重新上传。作者说要自己插图，就把改好的图片单独发过去，按文中顺序编号。
- 作者逐段提意见时，先按意见改，再**主动检查后面的章节有没有同类问题**，一并改掉，并列出改了哪些地方。
- 改完要做一遍标点检查，包括英文直引号、混进中文里的半角标点、多余空格和段尾标点。
- 每次修改后告诉作者改了什么，原句和新句并排列出来最清楚。
- 每次改完，告诉作者全文现在有多少字，给出不含空格的总字数，以及其中的汉字数。
- 作者说"稍微扩充一点"时，只扩核心论证，用新查到的事实和案例去扩，不加新章节，不画蛇添足。
- 作者指出写得不好时，先直接承认，再按意见把全文同类问题一起改掉，不辩解。

### 作者问"是不是合理"时，先分析，不要附和

作者说"先不要赞同，分析一下"时，先拆开每一段各在讲什么，指出问题具体出在哪一句和哪一句之间，再给两到三种改法并说明倾向哪种。确实没问题，也要说清楚为什么没问题。

### 读者视角审稿

作者让"检查一下改动小、收益高的地方"时，以一个第一次读这篇文章的读者身份通读全文，按值得改的程度排序列出问题，每条都给出原句和改法。重点看下面这些。

- 事实和数字的含义有没有写错，图片内容和正文是否一致
- 章节标题和内容是否对得上
- 因果词、转折词是否成立
- 有没有跳出来的旁白句
- 悬念有没有被中间插进来的内容打断，能不能只靠挪动整节来解决
- 首尾、相邻段落有没有撞词
- 同一事物的说法是否统一，"今年"这类相对时间
- 手机上过长的段落
- "据第三方数据"这类模糊来源，能补具体名字就补上

只列出来，等作者点头以后再改进文件。

### 换对话时做交接

作者要新开对话继续时，把这个选题的讨论整理成一份交接 Markdown，内容包括写作要求、作者的原话、当前大纲、待核实的数据和引语处理方式、拆出去的选题，以及新对话从哪一步开始。
